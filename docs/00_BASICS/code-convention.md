# 코드 컨벤션 & 협업 규칙

여러 명이 함께 개발하므로, **문서를 먼저 읽고 → 코드를 짠다**. 순서를 지키자.

## 1. 코드 작성 규칙

- **기능 분리**: 한 파일/모듈은 한 가지 일만. 커지면 쪼갠다.
- **의존성 낮추기**: 다른 기능의 내부 구현을 직접 참조하지 않는다. 공개된 인터페이스(함수/타입)로만 소통한다.
- **네이밍**: 역할이 드러나게. 축약어 남발 금지.
- **주석**: 왜 이렇게 했는지가 안 보일 때만. 코드로 설명 가능하면 주석 대신 코드로.

## 2. 문서화 규칙

- **코드 짜기 전에 관련 문서(`features/`, `system/`)를 먼저 확인**하고, 그 내용을 기반으로 작업한다.
- **기능 개발** → `features/` 안에 문서화 (무슨 기능인지, 어떻게 쓰는지).
- **시스템/구조 변경** → `system/` 파일을 수정 (공통 설정, 아키텍처, 빌드 등).
- **다른 기능이 쓰는 인터페이스**(공개 함수 시그니처, 입출력, 이벤트 등)는 반드시 문서로 제공한다. 인터페이스가 바뀌면 문서도 같은 커밋에서 고친다.

## 3. 협업 흐름

1. 작업할 부분의 문서를 읽는다.
2. 필요하면 문서를 먼저 갱신하고 팀과 합의한다.
3. 코드를 짜고, 문서와 어긋나지 않게 맞춘다.
4. 공개 인터페이스가 바뀌었으면 문서 업데이트를 같은 PR에 포함한다.

## 원칙

문서와 코드가 다르면 그건 버그다. 항상 같이 움직인다.
