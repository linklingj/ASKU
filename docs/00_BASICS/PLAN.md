# 대학 웹사이트 자동 QA 시스템 기획 문서

## 1. 프로젝트 개요

대학교 웹사이트를 크롤링해 자동으로 QA 시스템을 구축하는 프로그램이다.
LLM과 Graph RAG를 결합해 학교 정보를 수집하고, 근거를 포함한 답변을 제공한다.

사용자는 두 가지 방식으로 시스템을 이용한다.

- **신규 등록**: 학교명과 공지사항 URL을 입력하면 자동 크롤링 후 지식그래프를 생성한다.
- **기존 접근**: 이미 등록된 학교는 이름 검색만으로 바로 질문할 수 있다.

---

## 2. 목표

- 학교별 정보를 수작업 없이 자동으로 구조화한다.
- 자연어 질문에 정확하고 근거 있는 답변을 제공한다.
- 주기적 크롤링으로 최신성을 유지한다.
- 로컬 LLM과 API LLM을 선택적으로 사용한다.

---

## 3. 핵심 기능

| 기능 | 설명 |
|------|------|
| 학교 등록 | 공지 URL 첨부 → 자동 크롤링 → 지식그래프 생성 → 서버 저장 |
| 학교 검색 | 학교명 검색으로 기존 지식그래프 접근 |
| 정보 추출 | 크롤링 문서에서 중요 정보를 LLM으로 추출 |
| 지식그래프 | 엔티티·관계 기반 그래프 구축 및 저장 |
| Graph RAG 답변 | 그래프 + 벡터 검색으로 컨텍스트 구성 후 답변 생성 |
| 근거 제공 | 답변에 출처 링크·원문 문서 첨부 |
| 주기적 갱신 | 스케줄러로 재크롤링해 지식 업데이트 |
| LLM 선택 | 로컬(Ollama 등) / API(OpenAI·Anthropic 등) 전환 |

## 4. 시스템 아키텍처

```
[사용자] 
   │
   ▼
[프론트엔드]  ──  학교 등록 / 검색 / 채팅 UI
   │
   ▼
[백엔드 API (FastAPI)]
   │
   ├──► [크롤러]        ── 공지·학사 페이지 순회, HTML 수집
   │        │
   │        ▼
   │   [정보 추출기]     ── LLM 기반 엔티티·관계·청크 추출
   │        │
   │        ▼
   │   [그래프 빌더]     ── 노드·엣지 생성, 임베딩 생성
   │        │
   │        ▼
   │   [저장소]          ── Graph DB + Vector DB + 원문 저장
   │
   ├──► [Graph RAG 엔진] ── 그래프 순회 + 벡터 검색 + 답변 생성
   │        │
   │        ▼
   │   [LLM 추상화 레이어] ── 로컬 / API 라우팅
   │
   └──► [스케줄러]       ── 주기적 재크롤링 트리거
```

## 5. 데이터 흐름

### 5.1 등록 (신규 학교)

1. 사용자가 학교명 + 공지 URL 입력.
2. 크롤러가 링크를 따라 페이지를 순회하며 HTML 수집.
3. 각 페이지를 청크 단위로 분할.
4. LLM이 청크에서 엔티티·관계·핵심 정보 추출.
5. 그래프 빌더가 노드·엣지 생성, 각 청크를 임베딩.
6. Graph DB와 Vector DB에 저장, 학교 인덱스에 등록.

### 5.2 질의 (답변 생성)

1. 사용자가 학교 선택 후 질문 입력.
2. 질문을 임베딩하고 핵심 엔티티 추출.
3. 그래프에서 관련 노드를 순회(local search)하고, 벡터 DB에서 유사 청크 검색.
4. 검색 결과로 컨텍스트 구성.
5. 선택된 LLM이 답변 생성.
6. 근거가 된 원문 링크·문서를 답변과 함께 반환.

## 6. Graph RAG 설계

일반 벡터 RAG는 단편 검색에 강하지만, 관계 기반 질문에 약하다.
Graph RAG는 엔티티 간 관계를 명시적으로 다뤄 복합 질문에 강하다.

### 6.1 엔티티 예시

학과, 부서, 공지, 학사일정, 장학금, 담당자, 연락처, 규정, 시설, 신청 절차.

### 6.2 관계 예시

- `공지` —소속→ `학과`
- `장학금` —마감일→ `날짜`
- `담당자` —연락처→ `전화/이메일`
- `절차` —선행조건→ `절차`

### 6.3 검색 전략

- **Local search**: 특정 엔티티 주변을 탐색. "○○장학금 마감일" 같은 구체 질문에 사용.
- **Global search**: 커뮤니티 요약을 활용. "장학금 종류 전체" 같은 포괄 질문에 사용.
- **Hybrid**: 그래프 순회 결과 + 벡터 유사도 결과를 결합해 컨텍스트 구성.

## 7. 데이터 모델

### 7.1 학교 (School)

| 필드 | 설명 |
|------|------|
| school_id | 고유 ID |
| name | 학교명 |
| base_url | 공지·학사 기준 URL |
| graph_ref | 지식그래프 참조 |
| created_at / updated_at | 생성·갱신 시각 |
| crawl_schedule | 재크롤링 주기 |

### 7.2 문서 (Document)

| 필드 | 설명 |
|------|------|
| doc_id | 고유 ID |
| school_id | 소속 학교 |
| source_url | 원문 링크 (근거 제공용) |
| title / content | 제목·본문 |
| crawled_at | 크롤링 시각 |
| embedding_ref | 벡터 참조 |

### 7.3 그래프 노드·엣지

- 노드: `type`, `name`, `attributes`, `source_doc_ids`
- 엣지: `source`, `target`, `relation`, `source_doc_ids`

> 모든 노드·엣지는 `source_doc_ids`로 원문과 연결되어 근거 추적이 가능하다.

## 9. LLM 추상화 레이어

로컬과 API를 동일 인터페이스로 다룬다.

```
LLMProvider (인터페이스)
 ├─ generate(prompt, context) → answer
 ├─ embed(text) → vector
 └─ extract_entities(text) → entities, relations

구현체:
 ├─ OllamaProvider  (로컬)
 ├─ OpenAIProvider  (API)
 └─ AnthropicProvider (API)
```

사용자 설정에서 제공자를 전환한다.
추출·임베딩·답변 단계별로 다른 제공자를 지정할 수도 있다.

## 10. 주기적 갱신

- 학교별 크롤링 주기를 설정한다(예: 매일·매주).
- 스케줄러가 주기마다 재크롤링을 실행한다.
- 신규·변경 문서만 감지해 그래프를 증분 업데이트한다.
- 삭제된 공지는 만료 처리한다.

> 변경 감지는 URL·본문 해시 비교로 처리해 불필요한 재처리를 줄인다.

## 11. API 설계 (초안)

| 메서드 | 엔드포인트 | 설명 |
|--------|-----------|------|
| POST | `/schools` | 신규 학교 등록 + 크롤링 시작 |
| GET | `/schools?query=` | 학교명 검색 |
| GET | `/schools/{id}` | 학교 상세 |
| POST | `/schools/{id}/query` | 질문 → RAG 답변 |
| POST | `/schools/{id}/recrawl` | 수동 재크롤링 |
| GET | `/schools/{id}/status` | 크롤링·인덱싱 상태 |

답변 응답 예시:

```json
{
  "answer": "○○장학금 마감일은 3월 15일입니다.",
  "sources": [
    { "title": "2026 교내 장학금 안내", "url": "https://..." }
  ]
}
```

## 13. 리스크 및 고려사항

- **크롤링 정책**: 대상 사이트의 robots.txt·이용약관 준수, 요청 속도 제한.
- **구조 다양성**: 학교마다 페이지 구조가 달라 파서 일반화가 어렵다. LLM 추출로 완화.
- **정보 최신성**: 갱신 지연 시 오답 위험. 주기 조정과 갱신 시각 표기로 대응.
- **환각(hallucination)**: 근거 문서를 강제 인용하고, 근거 없으면 답변을 보류한다.
- **로컬 LLM 성능**: 추출·답변 품질이 모델 크기에 좌우된다. 작업별 모델 분리 권장.
- **개인정보**: 담당자 연락처 등 민감 정보 노출 범위를 정책으로 관리한다.
