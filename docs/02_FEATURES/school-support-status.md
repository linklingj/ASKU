# 학교 지원 현황과 남은 작업

새 학교를 붙이는 일이 어디까지 자동이고 어디부터 사람 손이 필요한지 적는다.
학교를 추가하거나 수집이 깨졌을 때 여기부터 본다.

측정은 모두 `scripts/check_schools.py` 로 실제 사이트를 받아 확인한 값이다.
목록 1페이지 + 상세 2건 기준이며, 서비스는 더 많이 수집하므로 깊은 페이지의
어긋남은 여기서 잡히지 않는다.

```bash
PYTHONPATH=backend python3 backend/scripts/check_schools.py "이름=URL"
PYTHONPATH=backend python3 backend/scripts/check_schools.py --file schools.txt --autogen
```

## 1. 수집 규격을 정하는 순서

```text
전용 어댑터 클래스  →  저장된 규격  →  학교별 규격  →  알려진 템플릿
                                              →  (설정 시) LLM 생성  →  공용 파서
```

손으로 검증한 전용 클래스가 가장 앞이다. 자동 생성 규격이 잘못돼도 이미 검증된
학교는 영향을 받지 않는다.

**학교별 규격**(`spec_templates.HOST_SPECS`)은 알려진 게시판 제품을 쓰지 않아
손으로 쓴 규격이다. 제품 템플릿이 여러 학교가 한 장을 공유하는 반면 이쪽은 학교
하나가 한 장을 쓴다. 저장이 DB 에만 남으면 DB 를 새로 만들 때 그 학교들이 전부
공용 폴백으로 떨어지므로 저장소에 둔다. 같은 제품을 쓰는 학교가 뒤에 나오면
그때 템플릿으로 올린다.

규격의 정본은 DB 다. 크롤은 저장된 규격을 먼저 보므로, 이미 등록된 학교는 나중에
`HOST_SPECS` 를 추가해도 갱신되지 않는다 — 그 경우 DB 쪽을 덮어야 한다.

어느 단계로도 정해지지 않으면 공용 파서로 수집하고, 그 결과는 수집 품질 지표에
남는다([`03_crawler.md`](../01_SYSTEM/03_crawler.md) §6-2).

LLM 생성은 기본으로 꺼져 있다(`SPEC_AUTOGEN`). 호출당 약 4만 토큰이라 무료 티어는
학교 몇 개면 한도에 걸린다.

## 2. 학교별 현황

### 수집 가능

| 학교 | 방법 | 목록 | 제목 | 날짜 | 비고 |
|---|---|---|---|---|---|
| 연세대 | 전용 클래스 | 22행 | 100% | 100% | 본문은 공용 파서 |
| 세종대 | 전용 클래스 | 16행 | 100% | 100% | 하위 게시판 9개 등록 |
| 홍익대 | 전용 클래스 | 10행 | 100% | 100% | 본문 K2Web 파서 |
| 성균관대 | 전용 클래스 | 25행 | 100% | 100% | |
| 아주대 | `k2web` 템플릿 | 20행 | 100% | 100% | 장학공지 자동 발견 |
| 이화여대 | `k2web` 템플릿 | 19행 | 100% | 100% | 장학공지 자동 발견 |
| 건국대 | `artclview` 템플릿 | 88행 | 100% | 100% | 하위 게시판 4개 자동 발견 (아래 주의) |
| 서울대 | 학교별 규격 | 8행 | 100% | 100% | 하위 게시판 3개 자동 발견 |
| 국민대 | 학교별 규격 | 20행 | 100% | 100% | 하위 게시판 8개 자동 발견 |
| 고려대 | 학교별 규격 | 10행 | 100% | 100% | 상세 링크를 `onclick` 에서 조립 |
| 경희대 | 학교별 규격 | 10행 | 100% | 100% | 상세 링크를 `href` 의 `view()` 에서 조립 |
| 한양대 | 학교별 규격 | 20행 | 100% | 100% | 표가 아니라 `div` 목록 |
| 중앙대 | 학교별 규격 | 15행 | 100% | 100% | **목록만 브라우저 렌더링** |

아주대·이화여대·건국대는 **코드 추가 없이** 붙었다. 템플릿 방식이 실제로 작동한
사례다.

> **건국대 — 게시판 URL 주의 (2026-08-10 수정)**
>
> 처음 등록한 `/bbs/konkuk/25/artclList.do` 는 학교가 게시판을 폐지해 더는 목록을 주지
> 않는다. 대신 **HTTP 200 에 "사용중지된 싱글 모듈입니다" 알림 페이지**(7KB, `<title>관리모드
> &gt; 알림메세지</title>`)를 돌려줘, 크롤러는 네트워크 오류 없이 목록 0행을 읽고
> `NO_LISTING_ROWS` → `status: failed` 로 끝났다. 재시도로는 절대 복구되지 않는 종류다.
>
> 현행 게시판은 234(학사)·235(장학)·237(국제)·238(학생)·240(일반)·243(채용) 대역이다.
> 등록 URL 은 게시판 번호가 아니라 **메뉴 번호를 쓰는 `subview.do`** 로 둔다:
>
> | 등록 URL | 목록 | 하위 게시판 발견 |
> |---|---|---|
> | `/konkuk/2238/subview.do` (채택) | 26행 | **4개** (공지사항·학칙 개정 사전공고·장학공지·기타외부연구과제공고) = 합계 88행 |
> | `/bbs/konkuk/234/artclList.do` | 26행 | 0개 — 그 게시판만 돈다 |
>
> 게시판 URL 에는 좌측 메뉴가 없어 `find_boards` 가 형제 탭을 찾을 단서를 얻지 못한다.
> 연세대가 이미 `subview.do` 로 등록되어 있는 것과 같은 이유다.
>
> 남은 한계: 첨부 링크가 확장자 대신 `download.do` 로 나가서 `artclview` 템플릿의
> 확장자 기반 선택자로는 첨부 메타데이터가 0건이다(본문 수집에는 영향 없음). 고려대가
> 같은 문제를 `a[href*='/ctt/bb/bulletin']` 로 푼 선례가 있다 — 같은 템플릿을 쓰는
> 연세대에도 영향이 가므로 별도 검증 후에 손댄다.

## 3. 남은 작업

순서는 **쉽고 확실한 것부터**다. 앞의 것을 마치면 이 표의 상태를 갱신한다.

- [x] **국민대 — 규격 작성 완료**
      목록이 표가 아니라 `div.board_list > ul > li` 였다. 규격 한 장으로 해결됐고
      하위 게시판 8개도 자동으로 발견된다. 이 과정에서 일반 결함 세 가지를 함께
      고쳤다 — `form` 을 통째로 지워 본문이 사라지던 문제, 페이지 번호가 1부터인
      게시판에서 페이지네이션이 제자리이던 문제, 본문 후보가 비어도 다음 후보로
      넘어가지 않던 문제.
- [x] **서울대 — 규격 작성 완료**
      지적 0건으로 통과한다. 날짜(`2026. 7. 31.`)를 읽지 못한 것은 파서가 구분자
      뒤 공백을 허용하지 않아서였고, 제목을 잃은 것은 글 제목이 `<header>` 안에
      있는데 잡음 제거가 먼저 지웠기 때문이다. 둘 다 일반 결함이라 파서를 고쳤다.
- [x] **고려대·경희대 — 규격에 링크 조립 규칙 추가 완료**
      두 학교 모두 상세 링크가 자바스크립트 호출에만 있었다. 학교마다 코드를 짜는
      대신 규격에 `detail_link_attr`·`detail_link_pattern`·`detail_link_template`
      을 두어, 번호를 뽑아 상세 URL 을 조립하게 했다. 페이지네이션을 유형으로
      나눈 것과 같은 방식이라 다음 학교도 규격 한 장이면 된다.
      고려대에서 일반 결함 하나를 함께 고쳤다 — 사이트가 닫는 태그를 흘리면
      html.parser 가 뒤따르는 내용을 `<input>` **안쪽**으로 넣는데, 잡음 제거가
      그 입력 요소를 통째로 지워 게시글 본문까지 사라졌다. 이제 다른 요소를
      품고 있으면 껍데기만 벗겨 낸다.
- [ ] **국민대 — 같은 게시판이 두 번 등록되는 문제**
      `/user/enGuid/3/` 와 `/user/kmuNews/notice/3/` 가 같은 글 11건을 돌려주는데
      주소가 달라 지문 중복 제거가 걸러 내지 못한다. 같은 공지가 두 번 저장된다.
      지문을 목록 내용 기준으로 비교하도록 손봐야 한다.
- [ ] **서강대 — 공지 URL 찾기**
- [x] **한양대·중앙대 — 완료**
      두 학교를 "동적 사이트"로 묶어 두었던 것이 틀렸다. 측정해 보니 갈렸다.

      | | 정적 HTML | 렌더링 후 |
      |---|---|---|
      | 한양대 | 공지 20건 | 20건 (동일) |
      | 중앙대 | 공지 0건 | 15건 |

      한양대는 렌더링이 전혀 필요 없었다. 표가 아니라 `div.hyu-list-body-item`
      목록이라 `table tbody tr` 로 세면 0행으로 보였을 뿐이다. 규격 한 장으로 끝났다.

      중앙대만 Playwright 를 쓴다. 규격의 `render` 로 켜고, 값은 세 가지다 —
      `off`(기본) / `listing`(목록만) / `always`. 중앙대는 상세가 정적이라
      `listing` 이면 충분하다. 공지 300건이면 브라우저 호출이 300번에서 몇 번으로
      줄어든다.

      robots.txt·요청 간격·수집 예산·허용 호스트는 정적 요청과 똑같이 적용된다 —
      렌더링은 `_fetch` 안쪽에서만 갈린다. 렌더링 실패는 조용히 0건으로 넘기지
      않고 `RENDER_FAILED`·`RENDERER_UNAVAILABLE` 로 남겨 품질 지표에 드러낸다.

## 4. DB 초기 등록

검증을 통과한 위 13개 학교는 다음 명령으로 `schools` 테이블에 등록한다.
이 명령은 **크롤링·Gemini 호출을 시작하지 않으며**, 이미 같은 호스트가 있으면
중복 행을 만들지 않고 이름·기준 URL만 갱신한다.

```bash
# 등록 대상만 확인
PYTHONPATH=backend python3 backend/scripts/seed_schools.py --dry-run

# 로컬 또는 운영 DB 등록
PYTHONPATH=backend python3 backend/scripts/seed_schools.py

# Docker 배포 환경에서 등록
docker compose exec api python -m app.seed_schools
```

운영 배포 시에는 DB가 준비된 뒤 이 명령을 한 번 실행한다. 수집은 그 다음 API의
등록/재크롤 요청 또는 Scheduler를 통해 별도로 시작한다.

## 5. 확인되지 않은 것

- **엔티티 추출 → 그래프 → 검색**: 공지 1건으로만 확인했다(아주대). 나머지는
  Gemini 무료 티어 할당량(429)에 막혔다. 학교 하나에 공지 수백 건이면 건당
  LLM 을 부르므로, 실제 서비스에는 유료 전환이 필요하다.
- **깊은 페이지**: 측정은 목록 1페이지 기준이다. 10페이지를 도는 실제 크롤에서
  페이지네이션이 어긋나는 경우는 수집 품질 지표로 확인한다.
